# 06 · Бриф на систему скиллов

**Статус:** не начато · **Дата:** 2026-08-14
**Читать вместе с:** `07_SKILLS_RESEARCH.md` (фактура по 257 героям — там
материал, здесь задача), `docs/data/07a_SKILLS_CORPUS.md` (сырьё под неё),
`01d` §1–5, `01e` §5, `DECISIONS.md` ADR-002 и ADR-016.

Документ написан как передача смены: следующая сессия должна начать работу с
него, а не с раскопок.

---

## Зачем это отдельный документ

Скиллы — единственная крупная система, которую нельзя добавить постепенно.
Причина в сакраменте.

Сакрамент (`01d` §5) — это пять ступеней прокачки, и каждая **переписывает
поведение скилла**, а не добавляет процентов: добавить цель, добавить эффект
при убийстве, сработать в начале боя. Замер по 1285 записям сакрамента
(`07` §4) показал, насколько это буквально: на пятой ступени уникальный текст
у **195 героев из 257**, то есть у трёх четвертей. Если скилл написан как
функция в коде, каждая такая ступень требует править код на каждого героя —
это сотни ветвлений и гарантированные ошибки.

**Поэтому архитектурное требование номер один: скилл — это ДАННЫЕ, а не
функция.** Сакрамент тогда становится списком модификаторов, применяемых к
описанию скилла перед боем, а движок остаётся один на всех.

Спроектировать это надо один раз и правильно. Отсюда и решение делать систему
отдельной сессией со свежим контекстом.

## Что уже готово и на что опираться

| Готово | Где |
|---|---|
| Кулдаун скилла на юнита | `world.ts` → `skillCd`, тикает в `runCombat` |
| Различение героя и рядового | `world.ts` → `isHero` |
| Кап урона по рядовым | `types.ts` → `SKILL_VS_SOLDIER_PCT = 15` |
| Событийный буфер для рендера | `events.ts`, флаги Crit/Counter/Splash/Miss |
| Одновременный тик | `settleTick` — урон копится и раскрывается разом |
| Балансный измеритель | `pnpm sim`, метрика «составов без управы» |

То есть половина машинерии уже стоит: скиллу есть где хранить кулдаун, есть
кому сообщить о срабатывании и есть чем измерить последствия.

Кап по рядовым подтверждён массово, а не единичным упоминанием: пометка
`only 10% damage to soldiers` стоит почти на каждом площадном скилле
первоисточника (`07` §5).

## Что решено и не переоткрывать

**Семь уровней скилла**, максимум `X + 6Y` (`01d` §3). Прокачиваются отдельным
ресурсом от уровня героя. Уточнение из `07` §3: рост от первого уровня к
седьмому в **70 случаях из 126 ровно ×2.5** — это общий коэффициент, а не
свобода дизайнера. Хранить `base` + ступень роста, не два независимых числа.

**Скилл не критует и не уклоняется** (`01e` §1). Обычная атака — вероятностный
канал, где решает матчап классов; скилл — гарантированный, где решает вложение
в героя. Разделение чистое, брать целиком.

**Контры на скиллы не действуют** (`01e` §1, разбор на TapTap). Только на
обычные атаки.

**Ручных кастов три, с кулдаунами, плюс авто-политика** (ADR-002). Ручной каст
даёт КРАЙ, а не победу: любой бой кампании обязан проходиться без единого
каста. Ручного выбора цели нет — скилл наводится сам.

### ⚠️ Что переоткрыть придётся

**Ключевая балансная формула из `CLAUDE.md` неполна** (`07` §1, ADR-016).
Проверка на 19 героях с триггером «шанс на обычную атаку» дала разброс
произведения `шанс × урон` от 6 до 150 — в 25 раз. Коридора нет, но структура
есть:

```
шанс × урон × число_целей × качество_выбора_цели + вес_нечисловых_эффектов
```

Galahad бьёт до пяти целей за 80 и станит; Dracula бьёт одну случайную за 150.
Старая формула посчитает Galahad вдвое слабее. На таймерных скиллах — а их 104
из 257 — та же величина `урон / период` гуляет от 0.8 до 240, в триста раз.
Единой балансной валюты у первоисточника нет вовсе. Пока не выведен вес
контроля и охвата — задавать урон формулой нельзя, и это первая работа сессии
по скиллам, а не последняя.

**Но работающая часть замысла уцелела: числа дискретны.** Шанс берётся из
{10, 25, 30, 40, 50, 60, 65}, урон — из пяти пресетов вида `50(200)%`, период —
из {2…15 с}. Дизайнер не пишет число, а **выбирает из списка**. Это и надо
кодировать вместо формулы: узкий пул значений, медиана произведения 80 как
якорь первого скилла.

**Трёхслойный триггер (таймер + дистанция + шанс) описан неверно.** Триггеров
десять, они **комбинируются в одном скилле**, и самый частый — не таймер, а
старт боя: 121 скилл из 257 (`07` §2). Поле триггера — список.

## Предлагаемая модель данных

Черновик, который следующая сессия обязана продумать заново, но который
показывает нужную форму. Отличия от версии до ресерча помечены `←`.

```ts
interface Skill {
  /** ← СПИСОК: срабатывает по любому из триггеров, они комбинируются */
  triggers: readonly Trigger[]
  /** гейт поверх триггера; 100 = срабатывает всегда */
  chancePct: number
  /** внутренний кулдаун прока в тиках; 0 = без ограничения */
  internalCdTicks: number
  targeting: TargetSelector
  targetCount: number
  effects: readonly Effect[]
}

type Trigger =
  /** ← 121/257 — пассивка, включается один раз и работает весь бой */
  | { kind: 'battleStart' }
  | { kind: 'timer'; periodTicks: number }        // 104/257
  | { kind: 'everyNAttacks'; n: number }
  | { kind: 'onEngage' }                          // первый контакт
  | { kind: 'onKill' }
  | { kind: 'onDamageTaken' }
  | { kind: 'onFatalDamage' }                     // предсмертный, обычно раз за бой
  | { kind: 'hpBelow'; pctThresholds: readonly number[] }  // 80/60/40/20
  | { kind: 'onStacks'; n: number }               // накопитель как триггер

/** ← значение уровня 1 + ступень роста вместо пары независимых чисел */
interface Scaled { base: number; growth: GrowthTier }   // ×2 | ×2.5 | ×3 | ×4

type Effect = {
  /** ← флаг переехал со Skill: у одного скилла эффекты диспеллятся по-разному */
  dispellable: boolean
  /** DURATION_BATTLE = -1 — «постоянно», 95 случаев в первоисточнике */
  durationTicks: number
} & (
  | { kind: 'damage'; amount: Scaled; channel: DamageChannel }
  | { kind: 'heal'; amount: Scaled }
  | { kind: 'shield'; pctOfMaxHp: Scaled }
  | { kind: 'buff'; stat: StatId; pctDelta: Scaled; stackMax: number }
  | { kind: 'control'; effect: ControlId }
)

/** ← pctOfMaxHp вынесен отдельно: он игнорирует защиту, у него своя шкала */
type DamageChannel = 'physical' | 'magic' | 'true' | 'pctOfMaxHp'
```

Селектор цели — **отдельная забота, дороже, чем кажется**: 22 скилла
первоисточника выбирают цель по позиции в строю (тот же ряд, сетка 3×3, зона
перед собой). Наш `targeting.ts` работает пространственным хэшем и лейном,
позиционных селекторов у него нет (`07` §6).

Сакрамент — список модификаторов к этому описанию:

```ts
/** ← ступень ссылается на СТРОКУ ОБЩЕЙ ТАБЛИЦЫ, а не несёт своё число */
type SacramentStep = { modifier: ModifierId } | { custom: SacramentMod }

type SacramentMod =
  /** S1–S2: 168 первых ступеней из 257 — плоский стат, скилла не касается вовсе */
  | { kind: 'flatStat'; stat: StatId; pctDelta: number; scope: 'hero' | 'squad' }
  | { kind: 'addTargets'; n: number }                  // главный рычаг усиления
  | { kind: 'addEffect'; effect: Effect }              // райдер «при каждом касте …»
  | { kind: 'scaleEffect'; index: number; pct: number }
  | { kind: 'addTrigger'; trigger: Trigger }           // ← add, не replace
  | { kind: 'replaceSkill'; skill: Skill }             // S5 (195/257) и Awakening
```

Применяется **до боя**, при сборке отряда: движок в бою видит уже готовый
скилл и ничего не знает про сакрамент. Это и есть то, ради чего нужны данные.

Три приятные новости из замера:

- две трети ступеней 1–2 — плоские статы, движка скиллов вообще не касаются;
- на 257 героев приходится **38 уникальных формулировок**, и проценты в них
  прибиты гвоздями (атака героя всегда +12%, HP +6%, защита +18%). Это
  справочник модификаторов: ступень хранит `modifierId`, а не своё число, и
  балансировать можно одной строкой сразу у сотни героев;
- усиление идёт прежде всего **охватом**: `+1 цель` встречается 34 раза, урон
  при этом не трогают. `addTargets` — главный модификатор, а не побочный.

Дорогая работа сосредоточена на пятой ступени: там уникальный текст у 195
героев из 257.

**Шестая система — Awakening** (`07` §10). У 32 героев поверх сакрамента есть
ещё до трёх ступеней, и устроены они дёшево: одна и та же способность в двух
настройках (40(70)% статов, раз в 10 с, 66 с → 70(100)%, раз в 8 с, 99 с).
Делать её в v1 не обязательно, но `replaceSkill` должен быть штатной операцией,
а не заплаткой под пятую ступень.

## Что придётся построить нового

**Главное и самое дорогое — таймерные эффекты на юните.** Баффы, дебаффы,
контроль и щиты живут N тиков и должны истекать. Это новые массивы в `World`
и отдельный проход истечения, а значит:

- удар по бюджету тика (сейчас 1.0 мс из 4 при 840 юнитах);
- удар по хэшированию — состояние эффектов входит в состояние симуляции;
- риск для детерминизма, если порядок применения и истечения не зафиксирован.

Ограничение по числу одновременных эффектов на юнита придётся ввести сразу,
иначе массив не влезет в SoA-раскладку.

**Второе по цене — позиционные селекторы.** Движку скилла нужен доступ к
формации (ряд, лейн, ранг), а не только к списку живых юнитов в радиусе.

Остальное дешевле: наведение по классам уже есть в `targeting.ts`, урон и
лечение — в `combat.ts`, кулдаун — в `skillCd`.

## Порядок работ

0. **Назначить бюджет словаря эффектов** (см. Q-16). Это решение первое,
   потому что оно определяет, какие ветки `Effect` вообще существуют.
1. **Вывести балансную величину** взамен опровергнутой формулы (ADR-016).
   Без неё урон скилла задавать нечем.
2. **Спроектировать данные скилла и сакрамента.** Проверить форму на четырёх
   реальных примерах из `07`: Valente (четыре триггера в одном скилле),
   Galahad (шанс на атаку, стан, до 5 целей), Kelly (урон в % от maxHP),
   Ne Zha (диспелл разный у эффектов одного скилла). Если форма их не
   покрывает — переделать до кода.
3. **Таймерные эффекты в `World`** + проход истечения + хэширование. Тесты на
   детерминизм до реализации.
4. **Движок скилла:** триггеры → наведение → эффекты. Один на всех.
5. **Три скилла-образца** разных типов: урон по площади, бафф отряда, контроль.
6. **Прогнать `pnpm sim`.** Метрика «составов без управы» обязана остаться 0.
7. Сакрамент — только после того, как пункты 1–6 зелёные.

## Открытые вопросы

**Q-13. Сколько скиллов у героя в v1 — один или два?**
В первоисточнике один активный плюс модификаторы сакрамента. Рекомендую один:
второй удваивает балансную работу, а читаемость боя (столп 2) роняет вдвое.

**Q-14. Есть ли скиллы у рядовых бойцов?**
В первоисточнике есть, но слабые, и в ремейке их **удалили ради
производительности** (`01e`, разбор патча). Рекомендую сразу не делать —
готовый ответ от студии, которая на этом обожглась.

**Q-15. Куда деть `SKILL_VS_SOLDIER_PCT`?**
Константа есть, кап реализован, но применять его пока не к чему: площадь у
базовой атаки мага откачена (ADR-015). Он оживёт вместе с первым площадным
скиллом героя, и именно там его надо проверить замером.

**Q-16. ⚠️ Сколько словаря эффектов брать — и это главный вопрос документа.**
Первоисточник умеет десять типов контроля, 43 призыва, 95 постоянных бонусов,
клонов и полиморф в овцу. И платит за это читаемостью: сообщество вынесло
расчёт боя на сторонний симулятор `mwrarchive.com`, а самый полный видео-гайд
по игре про механику скиллов не говорит **ничего** (`07` §8). Это прямой
контрпример нашему столпу 2.

Рекомендация — узкий словарь v1: урон (физический / магический / true /
%maxHP), лечение, щит, бафф-дебафф четырёх статов, стан, замедление. Не брать:
призыв, воскрешение, клон, полиморф, очарование, отражение. Расширять потом
по одному эффекту с замером — сузить словарь после реализации невозможно.

**Q-17. Общий кулдаун на пул заклинаний — брать ли?**
В ремейке все заклинания делят один кулдаун и **перетаскиваются на таймлайн**
до боя, плюс есть авто-каст (`07` §7). Это планирование заранее, а не реакция,
и со столпом 1 согласуется лучше, чем кнопки во время боя. Кандидат на правку
ADR-002. Оговорка: наличие авто-каста рядом с ручным таймлайном — признак, что
сам разработчик не уверен, что игрок справится.

## Что нужно от заказчика

Практически ничего — вся входная информация в репозитории. По существу три
вещи, и все они про решения, а не про материалы:

1. **Ответ на Q-13, Q-14, Q-16, Q-17** (или явное «решай сам» — тогда беру
   рекомендации выше). Q-16 — единственный, который дорого откатывать.
2. **Приоритет:** скиллы до плейтеста на 5 людях или после. Плейтест —
   формальный гейт фазы 2, и он до сих пор не пройден. Аргумент делать его
   раньше: скиллы меняют ощущение боя, и тестировать имеет смысл то, что
   ближе к финальному. Аргумент делать позже: текущая версия уже играбельна,
   а гейт висит.
3. **Арт для скиллов** — вопрос из `QUESTIONS.md`, который так и не закрыт.
   Пока хватает силуэтов и цифр, но скилл без визуального отклика нарушает
   столп 2: игрок не поймёт, что произошло.
