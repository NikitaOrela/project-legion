# P0-07 — Гейт fixed-point: результаты замера

**Дата:** 2026-08-13 · **Железо:** облачный контейнер, Node 22.22.2 (V8)
**Статус гейта: ✅ ПРОЙДЕН на V8. ⬜ Замер на iPhone SE 2020 / JavaScriptCore — не сделан.**

---

## Зачем этот замер

Единственный публичный бенчмарк fixed-point-библиотеки в JS даёт **24 нс на операцию** через обёрточное API (и 78 нс на BigInt-варианте). При бюджете **4 мс на тик** и **840 юнитах** это оставляет:

```
4 000 000 нс / 840 юнитов = 4762 нс на юнит за тик
4762 нс / 24 нс = ~198 fixed-операций на юнит
```

198 операций на юнит — тесно. Проверяли гипотезу: свободные функции над сырыми `int32` без классов и обёрток дадут кратно лучше.

---

## Результаты, 1 000 000 операций, массивы `Int32Array`

| Операция | Время | нс/итерация | Против нативного double |
|---|---|---|---|
| нативное `a * b` (double, референс) | 1.63 мс | 1.63 | 1.0× |
| **`fxMul`** | **13.41 мс** | **13.4** | 8.2× медленнее |
| `fxDiv` | 14.98 мс | 15.0 | 9.2× медленнее |
| **`fxSin` через таблицу** | **32.86 мс** | **32.9** | 20.2× медленнее |
| `Math.sin` (референс, **запрещён в sim**) | 106.46 мс | 106.5 | 65.4× медленнее |

Цифры включают обвязку цикла и чтение из `Int32Array` — то есть это **реалистичная стоимость в рабочем коде**, а не идеальный микробенч.

---

## Три вывода

**1. Гипотеза подтвердилась: 13.4 нс против 24 нс у библиотечного API — в 1.8 раза лучше.**

Пересчёт бюджета:
```
4762 нс на юнит / 13.4 нс = ~355 fixed-умножений на юнит за тик
```
С запасом. Реальная работа юнита за тик — движение, проверка дальности, расчёт урона — это единицы-десятки `fxMul`, а не сотни. Основная масса операций в симуляции вообще целочисленная (сравнения, инкременты), она идёт по цене нативной.

**2. Замедление 8.2×, а не 18×.** Обёрточный класс стоит примерно вдвое дороже свободных функций. Решение «никаких классов в fixed-point» окупилось. Это фиксируется как архитектурное ограничение: **любая обёртка над `Fx` — регресс производительности, не рефакторинг.**

**3. Таблица синуса в 3.2 раза быстрее `Math.sin` — детерминизм здесь достался бесплатно.**

32.9 нс против 106.5 нс. Мы отказались от `Math.sin` ради детерминизма и **получили ускорение в довесок**. Это редкий случай, когда правильное с точки зрения корректности решение ещё и быстрее.

Точность при этом не пострадала: четвертьволновая таблица на 1024 записи (4100 байт) даёт максимальную ошибку линейной интерполяции **0.50 LSB Q16.16** по всему обороту. Для сравнения, таблица на 256 записей дала бы ~4.9 LSB.

---

## Оговорка к цифрам

Изолированный замер в тесном цикле с регистровыми переменными даёт для `fxMul` практически нулевую предельную стоимость — V8 инлайнит функцию целиком. То есть **13.4 нс — это верхняя оценка**, включающая доступ к памяти; в горячем коде с локальными переменными будет заметно дешевле.

Для планирования берём консервативные 13.4 нс.

## Точность `fxInvSqrt`

Range reduction (`x = m · 4^k`, `m ∈ [1,4)`) плюс 5 итераций Ньютона:

| x | относительная ошибка |
|---|---|
| 0.001 | 0.35% (худший случай, край диапазона) |
| 0.5 … 255 | < 0.01% |
| 1000 … 30000 | < 0.10% |

Без range reduction Ньютон **расходился** при x > ~500: условие сходимости `x·y² < 3` нарушалось, и итерация уходила в отрицательные значения. Это зафиксировано тестом.
