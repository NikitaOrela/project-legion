# 03 · Техническая архитектура

---

## 1. Главное техническое требование

**Детерминированная симуляция.** Одинаковый вход (seed + формации + данные баланса)
= побитово одинаковый выход. Всегда, на любой машине, в любом браузере.

Это не роскошь. Из детерминизма вытекает всё остальное:

| Что даёт | Зачем |
|---|---|
| **Реплеи размером 200 байт** | seed + две формации вместо записи кадров |
| **Валидация PvP на сервере** | сервер пересимулирует бой, читер отсекается |
| **Балансный тулинг** | 10 000 боёв headless за секунды, воспроизводимо |
| **Регресс-тесты** | golden replay в CI: изменил формулу — увидел, что сломал |
| **Offline-first** | клиент считает бой сам, сервер лишь сверяет |

Если детерминизм не заложен с первого дня — переделывать придётся всё ядро.
**Поэтому Фаза 1 роадмапа — именно ядро, до всякой графики.**

## 2. Выбор стека

| Стек | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **TypeScript + PixiJS v8** | Всё в тексте → идеален для AI-ассистированной разработки. Мгновенная итерация. Headless-симуляция тривиальна (тот же код в Node). Деплой в веб за минуты. Порт на мобилки через Capacitor | Нужно писать свой ECS и рендер-слой. Нативная производительность ниже Unity | ✅ **Рекомендую** |
| **Godot 4 (C#)** | Бесплатный, сцены в тексте (`.tscn`) → тоже дружелюбен к AI. Хороший 2D. Экспорт на всё | Меньше готовых решений для мобильного F2P. C# на мобилках требует внимания | 🟡 Хорошая альтернатива |
| **Unity 6 (2D URP)** | Индустриальный стандарт мобильного F2P. DOTS/ECS для массовых юнитов. Огромный Asset Store, готовые SDK монетизации/аналитики | Бинарные сцены и префабы → AI-помощь заметно слабее. Тяжёлая итерация. Лицензия | 🟡 Если цель — коммерческий мобильный релиз с командой |
| **Cocos2d-x** (движок оригинала) | Историческая точность | Мёртвая экосистема для новых проектов | ❌ Нет |

### Рекомендация

**Начинаем на TypeScript + PixiJS.** Причины:

1. Боевое ядро пишется как **чистая библиотека без зависимостей** — оно
   переносится на любой движок потом. Ставки не заперты.
2. Вы работаете с Claude. Текстовый стек даёт AI полный доступ к проекту:
   он читает, пишет, тестирует и рефакторит всё. С Unity-префабами — нет.
3. Веб-билд = мгновенный плейтест по ссылке. Для калибровки баланса это критично.
4. Порт: Capacitor → iOS/Android, либо позже переписать рендер под Unity,
   сохранив ядро (оно на чистой математике).

Решение о движке для финального мобильного релиза откладывается до конца Фазы 3 —
к тому моменту вы будете знать реальные требования по производительности.

**Железное правило:** `packages/sim` не импортирует ничего из `render`, `app`,

ядра и возможность гонять его в Node, в воркере и на сервере.

## 4. Правила детерминизма

Нарушение любого — тихий рассинхрон, который найдётся через месяц.

### 4.1 Запрещено в `packages/sim`

| Запрет | Причина |
|---|---|
| `Math.random()` | Недетерминирован |
| `Date.now()`, `performance.now()` | Время не входит в симуляцию |
| Числа с плавающей точкой в игровой логике | Разный результат на разных CPU/JS-движках |
| `Math.sin/cos/sqrt/pow` напрямую | Реализации различаются между платформами |
| Итерация по `Object.keys()` без сортировки | Порядок не гарантирован |
| `Set`/`Map` итерация как источник порядка | Зависит от порядка вставки |
| `async`/`await`, промисы, таймеры | Порядок выполнения недетерминирован |
| Любые внешние API (сеть, DOM, storage) | Не воспроизводимы |

### 4.2 Обязательно

```typescript
// Фиксированная точка Q16.16 — вместо float
type Fixed = number;                     // int32, младшие 16 бит = дробь
const FP_SHIFT = 16;
const toFixed = (n: number): Fixed => Math.round(n * 65536) | 0;
const fpMul = (a: Fixed, b: Fixed): Fixed => Math.round((a * b) / 65536) | 0;
const fpDiv = (a: Fixed, b: Fixed): Fixed => Math.round((a * 65536) / b) | 0;

// Свои таблицы тригонометрии и корня (предвычисленные, целочисленные)
const SIN_TABLE = new Int32Array(1024);  // [0, 2π) → Q16.16
const fpSqrt = (x: Fixed): Fixed => { /* целочисленный Ньютон */ };

// Единственный RNG-поток, PCG32
class Rng {
  private state: number;
  constructor(seed: number) { this.state = seed >>> 0; }
  next(): number { /* PCG32 */ }
  nextBelow(n: number): number { return this.next() % n; }
}
```

**Правила исполнения:**
1. Фиксированный шаг: `TICK = 1/30` секунды. Рендер интерполирует, sim — нет.
2. Порядок обхода сущностей — строго по возрастанию `entityId`. Всегда.
3. Один RNG-поток на бой, порядок потребления фиксирован системами.
4. Система, добавляющая сущности, кладёт их в очередь; применение — в конце тика,
   в детерминированном порядке.
5. Смерти обрабатываются пакетно в конце тика, не сразу.

### 4.3 Тест-контракт (CI, обязательно)

```typescript
test('детерминизм: одинаковый seed → одинаковый результат', () => {
  const a = runBattle(12345, armyA, armyB, data);
  const b = runBattle(12345, armyA, armyB, data);
  expect(hashResult(a)).toBe(hashResult(b));
});

test('golden replay: старые бои дают старые результаты', () => {
  for (const g of loadGoldenReplays()) {
    expect(hashResult(runBattle(g.seed, g.a, g.b, g.data))).toBe(g.hash);
  }
});
```

Golden-реплеи ломаются при любом изменении баланса — это правильно. Их
переgenерируют осознанно, коммитом «rebalance: …», и diff показывает,
какие бои поменяли исход.

## 5. Производительность

**Цель:** 840 юнитов, 60 fps, iPhone SE 2020 / Android средний сегмент.
Бюджет на тик симуляции: **≤ 4 мс** (при 30 Гц это 12 % кадрового времени).

### 5.1 Симуляция

| Проблема | Решение |
|---|---|
| Поиск целей O(n²) = 705 600 проверок | **Пространственная хэш-сетка**, ячейка = макс. дальность атаки. Соседи: O(1) |
| Аллокации в горячем цикле → GC-фризы | **SoA на TypedArrays**: `Float32Array` заменён на `Int32Array` (фикс. точка), ноль объектов в цикле |
| Ретаргет каждый тик | Раз в 15 тиков (0.5 с), с **раскидкой по кадрам**: юнит `i` ретаргетится на тике `(i % 15)` |
| Разрешение столкновений | Только внутри ячейки сетки + 8 соседних |

### 5.2 Рендер

| Приём | Эффект |
|---|---|
| Единый спрайт-атлас на сторону | 1–2 draw call на всю армию |
| `ParticleContainer` (Pixi) для миньонов | Батчинг тысяч спрайтов |
| Интерполяция между тиками sim | Плавность 60 fps при sim 30 Гц |
| LOD: миньоны дальше 60 % экрана — 2 кадра анимации вместо 8 | −40 % работы аниматора |
| Пул объектов для всплывающего урона и партиклов | Ноль аллокаций |
| Culling за пределами вьюпорта | При зуме |

### 5.3 Бенчмарк-гейт в CI

```
tools/bench.ts: 840 юнитов, 180 секунд боя (5400 тиков)
FAIL если: среднее время тика > 4 мс ИЛИ p99 > 10 мс
```

Гоняется на каждом PR. Регрессия производительности не должна проходить незаметно.

## 6. Данные и баланс

### 6.1 Пайплайн

```
Google Sheets / CSV  →  build.ts  →  zod-валидация  →  data.json  →  sim
      ↑                                                              ↓
      └──────── balance-report.ts ← batch-sim.ts ←──────────────────┘
```

Дизайнер правит таблицы, не код. Билд валидирует схему и падает на ошибках
до рантайма. Хеш данных входит в реплей — реплей знает, на какой версии баланса снят.

### 6.2 Пример схемы

```typescript
export const HeroSchema = z.object({
  id: z.string().regex(/^[a-z0-9_]+$/),
  class: z.enum(['infantry','pikeman','paviser','cavalry',
                 'archer','arbalist','mage','healer']),
  stars: z.number().int().min(1).max(5),
  baseHp: z.number().int().positive(),
  baseAtk: z.number().int().positive(),
  baseDef: z.number().int().positive(),
  skillId: z.string(),
  procChance: z.number().min(0.2).max(0.8),
  // skillDamage НЕ хранится — вычисляется из SKILL_BUDGET / procChance
});
```

> Обратите внимание: `skillDamage` **не задаётся вручную**. Он выводится из
> инварианта (`02_GDD` §3.8). Дизайнер физически не может сломать баланс,
> вписав слишком большое число — система не даёт.

### 6.3 Балансный тулинг (без него баланс невозможен)

```bash
npm run sim -- --matchups=all --n=10000 --out=reports/winrates.csv
```

Отчёты:
- **Матрица винрейтов** архетип × архетип (цель: 45–55 % по всем парам)
- **TTK-распределение** — как быстро умирает каждый класс
- **Вклад в урон** по классам — нет ли класса-пустышки
- **Использование скиллов** — сколько раз прокнули, сколько урона дали
- **Мусорные юниты** — классы с винрейтом < 40 % против всех

Ручная балансировка авто-баттлера на 8 классах и 80 героях невозможна.
Только симуляция.

## 7. Сеть и сохранения

### 7.1 Offline-first

| Слой | Где живёт |
|---|---|
| Бой | Клиент. Всегда. Никогда не на сервере |
| Прогресс, инвентарь, гача | Локальный сейв (IndexedDB / файл), опциональная синхронизация |
| Кампания | Полностью офлайн |
| PvP | Асинхронный: скачал формацию врага → симулировал локально → отправил реплей |
| Лидерборды, сезоны | Онлайн, опционально |

**Проверка:** выдерните сеть — играется всё, кроме PvP и лидербордов.
Выключите сервера навсегда — игра остаётся играбельной. Это требование.

### 7.2 Античит для PvP

```
Клиент  → { seed, formationHash, replayResult }
Сервер  → пересимулировал тем же ядром → сверил хеш
          совпало? засчитал. нет? флаг + ревизия аккаунта
```

Работает только благодаря детерминизму. Сервер гоняет тот же `packages/sim`
(Node) — один код, два места исполнения.

### 7.3 Формат сейва

```typescript
{
  version: 3,                 // для миграций
  playerId: string,
  prestige: { level, xp },
  heroes: [{ id, level, stars, skillLevel, equipment: [...] }],
  formations: [Formation, Formation, Formation],
  inventory: {...},
  currencies: {...},
  campaign: { cleared: Set<stageId>, stars: {...} },
  checksum: string            // против ручной правки
}
```

Миграции сейвов пишутся **с первого дня**. Ломать прогресс игрока апдейтом нельзя.

## 8. Качество и CI

| Гейт | Инструмент | Порог |
|---|---|---|
| Типы | TypeScript strict | ноль ошибок |
| Линт | ESLint + правило «no float in sim» (кастомное) | ноль |
| Юнит-тесты | Vitest | покрытие `sim` ≥ 85 % |
| Детерминизм | golden replays | 100 % совпадение |
| Производительность | bench | тик ≤ 4 мс |
| Схема данных | zod при билде | валидно |
| Сборка | Vite | проходит |

Кастомное ESLint-правило, запрещающее в `packages/sim` числа с плавающей точкой,
`Math.random`, `Date`, `async` — это 30 строк и оно спасёт вам недели отладки.
